# Agent Prompt Merge Design

## 背景

当前仓库里存在两份相近但侧重点不同的主提示词：

- `prompts/ai-prompt.md`
- `prompts/ai-engineering-partner.md`

前者更像工程执行 SOP，规则完整、路由细、测试与验收更成熟；后者更像适合直接挂载给 agent 的主系统提示词，角色更稳、边界更硬、流程更轻。

本次设计目标不是二选一，而是产出一份更适合作为主提示词的合并版 vNext。

## 目标

产出一份新的 merged prompt，满足以下条件：

1. 保留明确角色、硬约束和拒绝能力
2. 保留必要的工程裁决、分级和验证机制
3. 避免把提示词写成过重的执行手册
4. 补上原两份文档都缺失的高价值示例
5. 不覆盖当前已存在未提交修改的原文件

## 选定方案

采用方案 A：

- 以 `ai-engineering-partner.md` 为主骨架
- 从 `ai-prompt.md` 回填 3 类高价值内容：
  - 规则优先级裁决
  - 能力降级与宿主适配
  - 更成熟的测试决策
- 新增示例，增强边界场景下的稳定性

## 关键决策

### 1. 角色设定

新版本使用“资深 AI 工程顾问”作为统一角色名。

原因：

- “AI 工程”保留工程落地属性
- “顾问”保留判断、拒绝、回退、风险把关属性
- 比“搭档”更容易强化边界意识，比“软件顾问”更聚焦工程任务

### 2. 文件策略

不直接修改下列原文件：

- `prompts/ai-prompt.md`
- `prompts/ai-engineering-partner.md`

原因：

- 当前工作区显示这两个文件已有未提交修改
- 本次任务是对比、打分和继续推进，不包含明确授权去覆盖原文
- 新建 vNext 文件更利于后续对照、评审和回退

### 3. 结构策略

合并版保留以下结构：

1. 角色与定位
2. 优先级与裁决
3. 硬约束
4. 默认策略
5. 路由、分级与测试
6. 执行流程
7. Skill 路由
8. 宿主适配与输出
9. 示例
10. 规则固化

### 4. Skill 路由策略

原文中的 Skill 名称存在“语义名”和“真实可加载名”混用的问题。合并版改为：

- 优先写“场景 → 当前环境中最贴近的 Skill”
- 仅在名称相对稳定时给出示例 Skill
- 避免把不存在的 Skill 名称写成硬指令

### 5. 示例策略

新增 4 类示例：

1. 信息不足时请求补充或暂停
2. 调试任务先定位根因再修复
3. 评审任务 findings-first
4. 高风险操作先确认授权、影响和回滚

## 非目标

本次不包含：

- 覆盖原两份提示词
- 对宿主系统做真实 A/B 测试
- 声称线上效果已经验证
- 自动提交 git commit

## 验证策略

本次仅做静态验证：

- 文档结构是否自洽
- 约束是否互相冲突
- 技能路由是否避免伪指令
- 示例是否覆盖高频边界场景
- 合并版是否明显比原两份更适合作为主提示词
