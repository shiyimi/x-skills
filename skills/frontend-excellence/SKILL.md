# Frontend Excellence

交付当前约束下真正优质的前端结果。

不要满足于“能用”“差不多”“先做完再说”。当结构明显次优、复杂度明显失控、验证明显不足时，不要假装任务已经完成。优先选择最简单、最显式、最容易验证和回滚的路径，同时保证正确性、可维护性、可扩展性、可读性与用户体验。

## 核心工作流

1. 先判断当前任务是否属于前端任务。
2. 在行动前先确定主任务模式。
3. 先读取核心 references，再按任务读取专题 references。
4. 先做复杂度判断，再进入实现、评审、调试或优化。
5. 在通过统一质量门禁之前，不要宣称任务完成。

## 必读核心 references

任何前端任务都先读取以下文件：

- `references/00-core-principles.md`
- `references/01-quality-gates.md`
- `references/02-task-routing.md`
- `references/03-simplification-discipline.md`

这四份文件共同定义总哲学、统一门禁、任务分流与复杂度治理规则，是整个 skill 的核心层。

## 主任务模式

在继续之前，必须先把任务归为一个主模式：

- 实现
- 重构
- 评审
- 调试
- 性能优化
- UI / 交互打磨
- 架构 / 方案

如果任务同时涉及多个方面，选一个最能代表主交付物的模式，其他方面作为次级关注点处理。不要一上来就直接写代码、给结论或报问题清单。

## 按任务加载 references

读取完核心层后，只加载当前任务真正需要的专题文件：

- 组件边界、拆分、组合、所有权、props 设计：读取 `references/10-component-architecture.md`
- 本地状态、服务端状态、URL 状态、派生状态、副作用、表单与异步流：读取 `references/11-state-data-effects.md`
- 渲染开销、列表、memo 化、惰性加载、虚拟化、交互卡顿：读取 `references/12-rendering-performance.md`
- 语义、键盘、焦点、反馈、错误提示、交互细节：读取 `references/13-accessibility-interaction.md`
- 布局、层级、响应式、视觉一致性、交互质感：读取 `references/14-styling-visual-quality.md`
- 验证策略、验收说明、未执行项、回滚说明：读取 `references/15-testing-verification-rollbacks.md`
- 评审、重构、调试：额外读取 `references/16-review-refactor-debug.md`
- React / Next.js 专项规则：按需读取 `references/30-react-next-adapter.md`

不要默认把所有 reference 全部加载进来。只读取与当前任务直接相关的文件，避免规则噪音盖过判断本身。

## 示例使用规则

`examples/` 不是第二套规范，而是用于校准触发、任务模式和输出重心的样例集。

在以下场景，主动读取对应示例：

- 用户要“做一个页面”或“补一个页面流程”时：读取 `examples/build-page.md`
- 用户要“重构组件”或“清理一个越来越乱的页面”时：读取 `examples/refactor-component.md`
- 用户要“评审性能问题”或“判断为什么这么卡”时：读取 `examples/review-performance.md`
- 用户说“页面太普通 / 太平 / 不够专业，想打磨界面”时：读取 `examples/polish-ui.md`

示例的作用是帮助快速贴近真实任务表达，不要把示例当成固定模板照抄。真正的规则来源仍然是 `SKILL.md` 与 `references/`。

## 默认工作方式

把“简化”视为制度，而不是风格偏好。

默认优先级：

- 先删除不必要复杂度，再新增结构
- 先把逻辑放回真正拥有它的边界，再考虑抽象
- 先做派生，再做冗余存储
- 先显式表达，再使用技巧和魔法
- 先证明问题存在，再引入性能优化
- 先隔离复杂度，再接受复杂度存在

不要因为历史实现已经很乱，就继续保护错误复杂度。尊重项目约定，但不要为意外复杂度背书。

## 必过门禁

在宣称任何任务“完成”“修复”“优化”之前，必须确认：

- 结果在结构上比之前更清晰，或已明确解释为什么必须接受新的复杂度
- 不是依靠补丁叠补丁来维持正确性
- 不是只处理了 happy path
- 与任务相关的空态、加载态、错误态、部分完成态已处理
- 基本可访问性和响应式没有被默默跳过
- 引入性能技巧时有证据或清晰理由
- 已执行与未执行项披露清楚
- 影响范围、残余风险与回滚边界清楚可说

门禁的详细定义放在 `references/01-quality-gates.md` 中。

## 输出契约

输出必须反映真实工作，不允许用强烈语气掩盖未验证事实。

无论当前任务是实现、评审、调试还是方案设计，输出都应根据场景体现：

- 结论或结果
- 核心依据或关键判断
- 结构 / 简化判断
- 实施策略或问题清单
- 已执行的验证
- 未执行项及原因
- 残余风险、权衡或未清债务
- 需要时给出回滚点或影响边界

没有证据时，不要写成“已修复”“已验证”“已优化”。

## React / Next.js 适配声明

React 与 Next.js 是第一版的重要目标，但它们不是全部前端问题的代名词。

框架专项规则统一放在 `references/30-react-next-adapter.md`。不要把 React / Next.js 的局部经验污染核心哲学，也不要把所有前端问题都硬解释成框架技巧问题。

## 语气与标准

保持高标准、精确、直接、建设性。

不要追求看起来高级，不要把抽象误当质量，不要把运动感误当进展。目标不是显得厉害，而是在真实约束下把事情做对、做好，并把复杂度压到最低。
