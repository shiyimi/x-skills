# 渲染与性能

在判断前端渲染成本、交互响应性和性能优化准入时读取本文件。

如果结构问题和性能技巧冲突，先收结构，再决定是否引入优化。

## 准入前提

开始做性能工作前，至少应有以下之一：

- 明确症状
- 明确瓶颈
- 明确风险
- 明确业务约束

不要因为“以后可能会慢”就提前堆缓存、memo 化、虚拟化或懒加载。

## 先查结构

优先检查这些问题：

- 状态影响范围过大
- 父组件驱动了无意义的大面积重渲染
- render 中反复做重转换
- 引用无意义地频繁变化
- 大对象或回调层层下传
- 组件边界让渲染责任失控

## 常见热点

性能问题通常集中在：

- 大列表和复杂表格
- 高频输入交互
- 拖拽、滚动、动画
- 重计算与重复转换
- 首屏加载与路由切换

不同热点对应不同手段，不要统一套模板。

## 证据与指标

不同症状优先看不同证据：

- 首屏慢：LCP、请求 waterfall、关键路径资源、首屏 bundle
- 交互迟钝：INP、输入 / 点击后的反馈延迟、React Profiler 或 flamegraph
- 大列表 / 复杂表格：行数规模、重复转换、commit 成本、滚动 / 筛选热点
- 路由切换慢：路由级 chunk、重挂载范围、loading 边界是否有效

如果没有基线症状或至少一个观察指标，不要轻易写成“已优化”。

## 默认优化顺序

通常按这个顺序推进：

1. 先锁定症状和当前证据
2. 先排除结构问题、状态影响范围和重复转换
3. 如果是 React / Next.js，再优先看等待链、客户端边界和 bundle / serialization 成本
4. 只有在瓶颈仍明确存在时，再引入局部 memo 化、虚拟化、懒加载或拆包

顺序错了，优化很容易变成“补技巧而不是治根因”。

## 技巧准入

默认不要无证据引入：

- `React.memo`
- `useMemo`
- `useCallback`
- 虚拟化
- `lazy` / `Suspense`
- 复杂拆包与延迟加载

只有在瓶颈明确、当前结构已足够清楚，且该技巧真的能解决当前问题时才考虑它们。

## 交互响应性

除了 FPS 和首屏，也要看：

- 输入延迟
- 点击后的反馈延迟
- 搜索、筛选、切页、弹窗是否拖泥带水
- 用户操作后是否能及时感知系统状态

很多“性能差”其实是反馈设计太弱。

## 输出义务

声称做了性能优化时，尽量说清楚：

- 症状是什么
- 问题本质更偏结构还是更偏性能
- 基线证据或关键指标是什么
- 引入了什么手段
- 为什么它在当前上下文合理
- 做了什么验证
- 哪些仍未验证
