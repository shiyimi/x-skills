# 简化制度

把简化视为必须遵守的工程制度，而不是“代码看起来更短”的偏好。

这里说的简化，不是盲目删代码，而是主动移除不必要复杂度，压缩认知负担，收紧边界所有权，并在保持正确性的前提下提升可维护性、可扩展性、可读性、可验证性与可回滚性。

## 默认决策顺序

默认按以下顺序做判断：

1. 先删除，再新增
2. 先归位，再抽象
3. 先派生，再存储
4. 先显式，再技巧化
5. 先证明，再优化
6. 先隔离复杂度，再接受复杂度

这六条不是风格提示，而是默认操作顺序。除非当前任务有充分理由例外，否则应先遵守它们。

## 六条规则的具体含义

### 1. 先删除，再新增

在新增结构之前，优先删除：

- 死分支
- 重复转换
- 无用状态
- 过时兼容残留
- 没有价值的浅包装

不要在已有浪费之上继续叠代码，如果这些浪费本来就可以先删掉。

### 2. 先归位，再抽象

先把逻辑放回真正拥有它的组件、模块或边界，再决定是否要提炼 hook、helper、util 或配置化抽象。

不要抽象错位的逻辑。先修正所有权，再讨论复用。

### 3. 先派生，再存储

如果一个值可以稳定地从现有状态、参数或数据推导出来，就不要再把它额外存成状态。

冗余状态会带来同步负担、隐含失效态和额外 effect。

### 4. 先显式，再技巧化

优先显式的输入、输出、状态迁移和数据流，而不是：

- 魔法 helper
- 隐式副作用
- 大而泛的配置系统
- 高压缩但难读的抽象

清晰永远比“看起来聪明”更有价值。

### 5. 先证明，再优化

不要在没有证据、没有明确瓶颈、没有具体风险的情况下，引入：

- memo 化
- 缓存
- 惰性加载
- 虚拟化
- 延迟渲染
- 复杂的渲染控制

不要用优化技巧掩盖弱结构。

### 6. 先隔离复杂度，再接受复杂度

当业务规则确实复杂时，把复杂度收进有明确所有权和命名的局部边界。

不要让复杂度泄漏到：

- 渲染树
- props 链
- 状态层
- 跨层 helper
- 不透明的配置对象

## 抽象准入规则

只有在以下条件大体成立时，才考虑新增抽象：

- 存在多个真实使用场景，而不是假想复用
- 输入输出边界已经足够稳定
- 抽象后降低的是认知复杂度，而不只是行数
- 抽象后更容易测试、验证或回滚
- 抽象后所有权依然清楚

以下理由不足以支撑抽象：

- 看起来重复，但其实仍然容易理解
- “以后可能会复用”
- 通用 hook 看起来更优雅
- 大配置对象似乎更灵活
- helper 把复杂度藏起来了

默认情况下，如果这些准入条件不成立，就不要抽象。

## 复杂度触发器

出现以下任一情况时，不要继续把任务当成纯实现问题处理，应先进入简化模式：

- 同一业务事实被存了多份
- 派生值通过状态或 effect 同步
- 一个组件同时负责请求、转换、编排、渲染和副作用
- 兼容层不断增加却没有退出边界
- hook、helper 或配置对象比它解决的问题更难懂
- 相同转换逻辑在多个分支里重复出现
- 条件渲染成了对状态建模的替代品
- memo 化或缓存被用来补结构漏洞
- props、context、事件只是机械透传
- 业务规则、UI 细节和副作用紧紧耦在一起

触发时，不要继续堆功能。先清结构。

## 简化操作顺序

进行前端简化时，按以下顺序执行：

1. 找出每个业务事实的单一事实源
2. 删除重复状态与重复转换
3. 把被存起来的派生值改回派生逻辑
4. 把副作用从渲染逻辑和纯计算中剥离
5. 把逻辑归还给真正拥有它的边界
6. 缩窄组件、hook、props、context 的职责范围
7. 最后再判断是否还需要抽象

不要跳过前面的步骤，直接去抽 hook 或抽 util。顺序错了，只会把坏结构固化得更深。

## 前端反模式黑名单

以下模式应视为强烈警报：

- 用 `useEffect` 当状态同步器
- 把表现层值或派生值存成长期状态
- 为一个具体页面提前造通用 hook
- 用巨大的配置对象隐藏真实业务规则
- props 跨很多层透传却没有清楚所有权设计
- 用 memo 化稳定一个本来就噪音很多的渲染路径
- 把请求、归一化、编排和渲染塞在一个组件里
- 为兼容旧结构不断增加包装层
- 新增 helper 的速度快于删除旧逻辑的速度
- 把所有复杂度问题都解释成性能问题

这些模式不一定在任何情况下都绝对禁止，但一旦出现，必须给出强理由。

## 实现、评审、重构时的行为要求

### 实现时

- 优先消灭复杂度，而不是装饰复杂度
- 优先一个清楚边界，而不是多个来路不明的 helper 层
- 优先局部清晰，而不是投机式通用
- 优先普通逻辑，而不是框架迷信

### 评审时

- 把可避免复杂度视为真实质量问题，而不是美学建议
- 把冗余状态、错位抽象、所有权混乱视为高优先级问题
- 在讨论风格之前先拦截复杂度扩散

### 重构时

- 先减少部件数量，再谈外观整齐
- 在安全前提下删旧路径，而不是只叠加新路径
- 始终让回滚边界保持局部、可见

## 最终输出义务

如果本轮工作显著受简化制度影响，最终输出必须明确说明：

- 删除了什么不必要逻辑
- 减少了哪些状态、分支或重复
- 澄清了哪些所有权边界
- 还有哪些复杂度没清掉
- 为什么这些复杂度暂时无法清掉
- 回滚边界在哪里

不要只写“结构更清晰了”。要说清楚到底简化了什么。
