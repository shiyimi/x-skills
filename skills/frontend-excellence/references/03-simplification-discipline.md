# 简化优先

任何前端任务都应先读取本文件。

当复杂度已经开始主导任务，或你怀疑“继续堆功能只会把结构推向更糟”时，更要让本文件主导当前处理方式。

目标不是盲目删代码，而是先移除不必要复杂度，再决定还需要什么结构。

## 复杂度触发器

出现以下任一情况时，先简化，再继续实现 / 调试 / 打磨：

- 同一业务事实被存了多份
- 派生值通过状态或 effect 同步
- 一个组件同时负责请求、转换、编排、渲染和副作用
- hook、helper 或配置对象比它解决的问题更难懂
- props、context 或事件只是机械透传
- 包装层不断增加却没有清楚退出边界
- 用 memo 化、缓存或渲染技巧补结构漏洞

## 默认顺序

按以下顺序收复杂度：

1. 找出单一事实源
2. 删除重复状态与重复转换
3. 把被存起来的派生值改回派生逻辑
4. 把副作用从渲染和纯计算中剥离
5. 把逻辑归还给真正拥有它的边界
6. 最后才判断是否需要新增抽象

不要跳过前面的步骤，直接抽 hook、抽 util 或加配置层。

## 默认偏好

- 先删除，再新增
- 先归位，再抽象
- 先派生，再存储
- 先显式，再技巧化
- 先证明，再优化
- 先隔离复杂度，再接受复杂度

工程化、组件化、模块化不意味着抽象更多或层次更厚，而意味着边界更清楚、职责更稳定、复杂度更收敛。

## 抽象准入规则

只有当以下条件大体成立时，才考虑新增抽象：

- 存在多个真实使用场景，而不是假想复用
- 输入输出边界已经足够稳定
- 抽象后降低的是认知复杂度，而不只是行数
- 抽象后更容易验证和回滚
- 抽象后所有权依然清楚

以下理由不足以支撑抽象：

- “以后可能会复用”
- “看起来更优雅”
- “先做成通用的再说”
- “helper 把复杂度藏起来了”

## 高风险反模式

出现这些模式时，应默认把它们当成警报：

- 用 `useEffect` 当状态同步器
- 把表现层值或派生值存成长期状态
- 为单一页面过早造通用 hook
- 用大配置对象隐藏真实业务规则
- 把请求、整形、编排和渲染塞进同一层
- 新增 helper 的速度快于删除旧逻辑的速度

## 输出义务

如果本轮明显依赖了简化优先，最终应说清楚：

- 删除了什么
- 减少了哪些状态、分支或包装层
- 澄清了哪些所有权边界
- 还有哪些复杂度暂时保留
- 为什么暂时保留
- 回滚边界在哪里
