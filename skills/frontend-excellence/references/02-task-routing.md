# 任务路由

主模式不清或任务混合时，读本文件。

## 主模式路由表

| 主模式 | 主交付物 | 默认读取 | 先盯什么 |
| --- | --- | --- | --- |
| 实现 | 新增或修改前端行为 | `10` `11` `13` `14` `15` | 结构是否稳定到值得继续扩展 |
| 重构 | 降复杂度、理顺边界、删冗余 | `16` `10` `11` `15` | 哪些复杂度是意外复杂度 |
| 评审 | 问题清单、风险判断、质量结论 | `16` `10` `11` `12` `13` `14` `15` | 什么是真问题，怎么按严重度排序 |
| 调试 | 缩小范围、定位根因、给修复路径 | `16` `11` `12` `13` `15` | 现象、证据、假设是否分开 |
| 性能优化 | 明确的性能改善 | `12` `11` `10` `15` | 是否真有瓶颈，还是结构问题伪装成性能问题 |
| UI / 交互打磨 | 提升完成度、层级、可信感、交互质感 | `14` `13` `15` | 问题是视觉 / 交互，还是结构本身 |
| 架构 / 方案 | 边界设计、状态模型、实现取舍 | `10` `11` `13` `14` `15` | 最简单可行边界是什么 |

React / Next.js 细节只在需要时补读 `30-react-next-adapter.md`。

任何主模式都先带着 `00-core-principles.md`、`01-quality-gates.md`、`03-simplification-discipline.md` 进入；`00` 定优先级，`03` 定简化顺序，`01` 定结论门槛。上表里的“默认读取”是在这三个必读入口之外的按需补充。

如果某个模式下的处理方式与 `03` 冲突，以 `03` 为准。

## 怎么选主模式

- 要落代码和行为，通常是实现
- 要减复杂度和清边界，通常是重构
- 要判断好坏和列风险，通常是评审
- 要找原因和修路径，通常是调试
- 要把卡顿变快，通常是性能优化
- 要把页面做得更专业、更顺、更可信，通常是 UI / 交互打磨
- 要回答“应该怎么设计”，通常是架构 / 方案

## 混合任务处理

- “先看为什么卡，再顺手给我改掉”
  - 主模式通常是调试，性能优化是后续动作
- “页面太乱，顺便把交互做顺”
  - 主模式通常是重构，UI / 交互打磨是次级关注点
- “帮我做这个页面，但现有状态流已经很混乱”
  - 主模式通常还是实现，但处理方式应立即切到 `03-simplification-discipline.md` 主导的简化优先
- “评审一下这个 PR，顺便看看为什么会闪”
  - 主模式通常是评审，调试作为附加分析

## 常见误判

- 把结构问题误当成调试问题
- 把所有卡顿都当成性能问题，而忽略状态或边界设计
- 把所有视觉问题都当成样式问题，而忽略信息层级与交互逻辑
- 把实现任务理解成“先写出来再说”
- 把重构当成“允许行为悄悄变化”的借口

## 何时升级到简化优先

- 重复状态
- effect 驱动的状态同步
- 包装层不断增加
- 所有权混乱
- 抽象先于问题稳定
- 用性能技巧掩盖结构问题
