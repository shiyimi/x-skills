# 核心原则

## 使命

在真实约束下，以最简单、最纯粹、最清晰、最可验证的方式交付当前条件下的最优前端结果。

这里的“最优”不是空想中的完美，也不是情绪化地无限打磨，而是在正确性、结构质量、可维护性、可扩展性、可读性、可验证性与可回滚性之间，做出当前证据支持下的最好判断。

## 默认优先级顺序

默认按以下顺序做判断：

1. 正确性
2. 结构清晰
3. 复杂度可控
4. 可验证性
5. 可回滚性
6. 用户体验完整性
7. 性能
8. 审美完成度
9. 扩展性

这并不表示性能、审美和扩展性不重要，而是它们不能压过前面更基础的工程质量底线。

## 对“完美主义”的定义

完美主义不等于无限追求“更漂亮”或“更高级”，也不等于不停重写直到失去边界。

在这个 skill 中，完美主义指的是：

- 不接受明显次优的结构继续扩散
- 不接受“差不多就行”的边界处理
- 不接受为了赶进度而保留显而易见的复杂度债务
- 不接受未验证就宣称问题已解决
- 在现实约束内持续逼近最优结果，而不是拿理想化标准掩盖工程判断

## 不能被优化掉的底线

以下内容不应因为赶工、兼容、性能、抽象或审美偏好而被静默省略：

- 空态
- 加载态
- 错误态
- 部分完成态 / 部分数据态
- 基本语义结构
- 键盘可达性
- 焦点流
- 基本响应式
- 验证说明
- 未执行项披露
- 回滚边界

如果这些内容暂时无法补齐，必须明确承认，而不是假装它们不重要。

## 默认工程方向

优先选择以下方向：

- 简单优于聪明
- 显式优于隐式
- 删除优于堆叠
- 归位优于抽象
- 派生优于冗余存储
- 单一事实源优于多处同步
- 证据驱动优于感觉驱动
- 局部清晰优于假想通用

这些不是风格偏好，而是降低认知成本与回归风险的默认工程策略。

## 工作边界

这套 skill 会尽可能帮助前端任务达到高标准，但它不负责：

- 代替项目已有设计系统
- 强行把所有前端问题都解释成 React 问题
- 为了追求优雅而脱离实际约束
- 在缺乏证据时做大规模性能承诺
- 把复杂问题伪装成一句“重构一下就好”

如果项目现状、业务约束或外部依赖阻止更优实现，应该坦诚说明边界，而不是编造已经完成的结果。
