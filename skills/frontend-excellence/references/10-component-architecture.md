# 组件架构

在判断组件边界、拆分方式、props 契约或抽象时机时读取本文件。

目标不是把组件拆得更碎，而是让所有权、输入输出和复用边界更清楚。

## 默认模型

- 父组件负责编排、边界控制和关键决策
- 子组件聚焦单一职责和清楚的输入输出
- 局部逻辑优先靠近真正拥有它的组件
- 先组合，再考虑“万能组件”或共享抽象

如果一个组件同时负责数据获取、转换、多个状态、多个交互、副作用和大段分支，它通常已经越界。

## 边界三问

开始拆分或重组前，先回答：

- 这个组件真正拥有什么状态和决策
- 它对外暴露什么契约
- 哪些事情明确不该由它负责

三问答不清时，先收边界，不要急着抽象。

## Props 规则

优先让 props 具备这些特征：

- 命名清楚，语义单一
- 输入输出明确
- 数量适中
- 不把父组件职责偷偷推回子组件

以下情况通常意味着该回头看边界，而不是继续加字段：

- 深层透传
- 一个 prop 承担多个语义
- 大对象 prop 隐藏真实依赖
- 大量布尔开关拼模式

## 何时拆分，何时不拆

通常值得拆分：

- 出现多个可清楚命名的区域
- 不同区域拥有不同状态或交互责任
- 某块逻辑已出现真实复用
- 内部分支已经明显拖累可读性

通常不值得为“看起来整洁”而拆分：

- 只是 JSX 偏长，但责任仍然单一
- 只是局部重复很少
- 拆分后只是把复杂度跨文件扩散

## 抽象准入

只有在以下条件基本成立时，才考虑共享组件或共享 hook：

- 存在多个真实场景
- 契约已稳定
- 抽出后更易理解，而不是更灵活但更难读
- 验证和回滚不会更难

不要为了假想复用提前抽象。

## 红旗

看到这些现象时，应优先怀疑组件架构有问题：

- props 透传层级过深
- 一个组件承担太多不相关责任
- 条件分支和副作用混在渲染层
- 共享抽象的参数数量不断增长
- 相同 UI 语义在多个组件中表达不一致

## 输出义务

如果本轮改动涉及组件边界，最终应说清楚：

- 组件职责如何重新划分
- 哪些 props、状态或逻辑被收回到更合适的边界
- 哪些拆分是真复用，哪些保留在本地
- 还有哪些组件层复杂度暂时保留
