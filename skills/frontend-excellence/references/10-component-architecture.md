# 组件架构

这份文件负责组件层面的边界设计、组合方式、职责划分和抽象时机。

组件架构的核心目标不是“拆得更碎”或“看起来更模块化”，而是让所有权更清楚、复用更真实、结构更容易理解。组件一旦失去边界，后续的状态流、性能、交互和测试都会跟着变差。

## 组件的默认职责观

优先遵循以下原则：

- 父组件负责编排、边界控制和关键状态汇合
- 子组件聚焦单一职责和清晰输入输出
- 展示组件不应偷偷持有过多业务判断
- 业务组件不应把展示细节、数据获取和副作用全部塞进自己

如果一个组件同时负责：

- 获取数据
- 转换数据
- 持有多个状态
- 编排多个交互
- 处理副作用
- 控制大块渲染分支

那它很可能已经越界。

## 边界设计

组件边界首先要回答三个问题：

- 这个组件真正拥有的状态是什么
- 这个组件对外暴露的契约是什么
- 这个组件不该负责的事情是什么

如果这三个问题回答不清，说明边界还不够稳定。

优先让以下内容靠近真正拥有它们的边界：

- 状态定义
- 派生逻辑
- 条件渲染判断
- 与该组件强绑定的样式与类型
- 局部工具函数

不要为了“代码看起来整洁”就把逻辑提前抽离得离组件太远。

## 组合优先于万能抽象

默认优先使用清楚的组合，而不是一开始就做“万能组件”。

优先：

- 多个职责清楚的小组件组合
- 明确的插槽 / children 组合
- 有边界的局部复用

谨慎：

- 参数很多的通用组件
- 各种模式切换型组件
- 通过大配置对象驱动所有行为的组件
- 一个组件试图覆盖多个业务语义

真正的复用应降低认知复杂度，而不是把复杂度挤进配置。

## Props 设计

好的 props 契约应该：

- 命名清楚
- 输入输出明确
- 责任归属清晰
- 数量适中

反模式包括：

- props 只是层层透传
- 一个 prop 同时承担多个语义
- 大对象 prop 掩盖真实依赖
- 通过布尔开关堆出多种模式
- 用回调把父组件职责偷偷推回子组件

当 props 越来越像“协议文档”而不是清楚契约时，优先回头检查边界，而不是继续加字段。

## 组件拆分准则

以下情况通常值得拆分：

- 一个组件包含多个独立可命名区域
- 不同区域有明显不同的状态或交互责任
- 某块逻辑的复用价值已经真实出现
- 某个局部区域难以测试或难以理解
- 组件内部条件分支已经影响整体可读性

以下情况通常不值得为了“好看”而拆分：

- 只是 JSX 行数偏长，但责任仍然单一
- 只是局部结构重复很少
- 拆分后只是把复杂度跨文件扩散
- 拆分后所有权反而更难看出

## 抽象时机

只有在以下条件基本成立时，才考虑抽成共享组件或共享 hook：

- 存在多个真实场景
- 契约已稳定
- 抽出来后更易理解，而不是更灵活但更难读
- 测试和验证更容易
- 回滚成本更低或至少不更高

不要因为“看起来可能会复用”就提前抽象。

## 渲染分支建模

复杂界面往往不是被 JSX 体积拖垮，而是被混乱的状态和分支拖垮。

优先：

- 先命名状态，再写分支
- 用清晰的阶段 / 结果建模代替散乱条件
- 把大分支放在真正拥有决策的边界

避免：

- 在深层 JSX 中堆大量三元表达式
- 多个局部条件共同决定同一业务状态
- 用视觉条件代替业务状态建模

## 文件与实现靠近归属者

在没有更强项目约定时，优先让以下内容同源邻近：

- 组件实现
- 局部样式
- 局部类型
- 局部测试

逻辑靠近归属者，能明显降低追踪成本。不要为了表面整洁，把相关内容拆得四散。

## 组件层常见问题清单

看到以下现象时，应优先怀疑组件架构有问题：

- props 透传层级过深
- 一个组件承担太多不相关责任
- 局部逻辑不得不依赖上层太多上下文
- 相同 UI 语义在多个组件中表达不一致
- 条件分支和副作用混在渲染层
- 共享抽象的参数数量不断增长

这些都不该被当成“随着项目变大很正常”。

## 输出时应说明什么

如果本轮工作涉及组件边界调整，最终说明尽量明确：

- 组件职责是如何重新划分的
- 哪些 props、状态或逻辑被收回到了更合适的边界
- 哪些拆分是真复用，哪些坚持留在本地
- 哪些复杂度仍然保留在组件层以及原因
