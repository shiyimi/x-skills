# React / Next.js 适配层

这份文件承接 React 与 Next.js 相关的具体规则，但它只是核心 skill 的适配层，不是核心哲学本身。

使用原则：

- React / Next.js 是第一版的重要目标技术栈
- 但不要把所有前端问题都硬解释成 React / Next.js 技巧问题
- 当框架规则与项目约定冲突时，优先以项目约定为准，并明确说明取舍

## 组件与命名

默认遵循以下命名与职责规则：

- 组件使用大驼峰命名
- hook 使用小驼峰命名并以 `use` 开头
- 布尔值优先使用 `is`、`has`、`should`
- 组件内部事件处理使用 `handleXxx`
- 对外暴露的事件 prop 使用 `onXxx`

职责边界建议：

- 父组件负责状态编排、数据流与边界控制
- 子组件聚焦单一职责和清晰输入输出
- 不要把页面组件写成“请求、转换、状态、渲染、副作用”全包的大容器

若项目没有更明确约定，优先让实现、样式、类型与测试文件靠近真正拥有它们的组件。

## 状态边界

默认按以下优先级思考状态：

- 服务端状态
- 本地状态
- URL 状态
- 全局状态

在 React / Next.js 中尤其要避免：

- 同一事实被多份状态持有
- 派生值被存成状态
- 用状态同步去维护本可直接推导的值

能通过 `props`、路由参数、服务端数据或已有状态稳定派生的内容，不要额外存起来。

## `useEffect` 使用边界

`useEffect` 应主要用于与 React 外部世界同步，例如：

- 订阅与退订
- 定时器
- 浏览器 API
- 必要的副作用协调

不要把 `useEffect` 当成以下用途的默认工具：

- 同步本可派生的数据
- 把 props 再复制进 state
- 让多个冗余状态勉强保持一致
- 以副作用修补边界设计问题

如果一个 effect 只是“当 A 变了，就 setState(B)”且 B 可以直接由 A 推导，优先回退到派生逻辑。

effect 一旦存在，应该问自己：

- 这个 effect 是否真的在同步外部世界
- 是否需要 cleanup
- 是否是在替代更清楚的状态设计

## `memo`、`useMemo`、`useCallback` 的准入规则

默认不要无证据地使用：

- `React.memo`
- `useMemo`
- `useCallback`

只有在以下场景中才考虑引入：

- 已存在明确性能问题或高频渲染热点
- 引用稳定性对下游接口或性能确实重要
- 经过验证，这个优化在当前结构下确实有意义

不要为了“看起来专业”就到处包一层 memo 化。

常见误用包括：

- 用 `useMemo` 缓存几乎没有成本的简单表达式
- 用 `useCallback` 包住所有事件处理函数
- 用 `React.memo` 掩盖父组件过度渲染
- 在结构本身噪音很大时依赖 memo 化止痛

先修结构，再谈这些优化。

## 组件设计偏好

在 React 中，优先以下模式：

- 清楚的 props 契约优于模糊的大配置对象
- 局部组合优于过早抽成“万能组件”
- 明确渲染分支优于隐藏状态魔法
- 数据流显式优于层层 helper 包装

避免以下模式：

- 一个自称“通用”的 hook 实际只服务一个页面
- 大量 props 透传但没有实际边界设计
- 组件同时持有数据获取、转换、业务规则与渲染细节
- 为假想复用提前做复杂抽象

## Next.js 边界意识

在 Next.js 中，尤其要明确服务端与客户端边界。

默认原则：

- 不需要交互、浏览器 API 或客户端状态时，优先保持服务端边界清晰
- 只有明确需要客户端能力时，再引入客户端边界
- 不要随手扩大客户端范围，让本可在更清楚边界中完成的逻辑全部滑向客户端

如果使用 `use client`，应该知道为什么需要它，而不是把它当成默认起手式。

同时注意：

- 服务端数据获取与客户端交互逻辑不要混成一团
- 组件边界要能看出谁负责数据、谁负责交互、谁负责呈现
- 不要把 Next.js 的约束当成掩盖结构问题的理由

## 渲染与交互性能

在 React / Next.js 中，优先从结构上控制性能问题：

- 缩小不必要的状态影响范围
- 减少无意义的父组件重渲染
- 避免在 render 中重复做重转换
- 避免把大对象和不稳定引用层层下传

以下技巧只在有证据时引入：

- `lazy`
- `Suspense`
- 虚拟化
- 复杂拆包与延迟加载
- 精细 memo 化

这些技术不是默认正确答案，而是为真实瓶颈服务的工具。

## 可访问性与语义

React / Next.js 项目里常见的便捷写法，很容易把语义和可访问性偷掉。

至少避免：

- 用 `div` 假装按钮
- 只绑定点击，不处理键盘交互
- 焦点流混乱
- 表单控件没有可理解标签
- 错误反馈只靠颜色传达

框架不会自动替你补这些责任。即便写法“能跑”，也不代表体验达标。

## 验证与表达

涉及 React / Next.js 的实现、重构、调试或优化时，最终说明应尽量明确：

- 哪些问题是结构问题
- 哪些问题是框架边界问题
- 哪些问题已经验证
- 哪些结论仍是推断
- 哪些优化没有执行验证

不要把“符合某个框架习惯”直接写成“已经是最优实现”。真正重要的是：它是否让当前代码更简单、更清楚、更可靠。
