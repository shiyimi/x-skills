# React / Next.js 适配层

只在任务真的依赖 React 或 Next.js 细节时读取本文件。

## 高杠杆优先级

在 React / Next.js 任务里，默认先按以下顺序看问题：

1. async waterfall 和等待链是否不必要地串行
2. 服务端 / 客户端边界是否过宽
3. 传到客户端的 bundle / serialization 成本是否过高
4. 状态设计和 effect 边界是否制造了额外渲染
5. 最后才考虑局部 memo 化和细节优化

不要一看到“卡”或“慢”就先堆 `useMemo`、`useCallback` 或 `React.memo`。

## 症状优先排查表

| 症状 | 先看什么 | 需要什么证据 | 常见假修复 |
| --- | --- | --- | --- |
| 首屏慢 | async waterfall、route 级 `use client`、首屏 bundle | LCP、网络 waterfall、路由级资源加载 | 先加 memo、先拆小组件 |
| hydration 闪烁 / 主题跳变 | 服务端与客户端事实源不一致、主题来源过晚 | 首屏录屏、SSR / CSR 状态差异、hydration 时序 | 再补一个 `useEffect` 同步 |
| 筛选 / 表单切换卡顿 | 状态影响范围、重复转换、客户端树过大 | INP、Profiler、状态变更影响图 | 到处加 `useCallback` |
| 路由切换抖动 | loading 边界、布局重挂载、低频重组件过早进入关键路径 | 路由切换录屏、layout / page 重挂载观察 | 只改动画时长 |
| 状态不同步 | URL、服务端、本地、派生值多事实源；effect 链 | 状态流日志、最小重现、事实源归属图 | 再补一个 effect 保持同步 |

## 数据获取与等待边界

- 独立请求尽量并行启动，而不是一层 `await` 完再进下一层
- 需要先把壳子显示出来时，优先考虑合适的 loading / `Suspense` 边界，而不是等所有数据准备好再整体返回
- 不要把数据获取、整形和交互状态都塞进同一个客户端组件

## `useEffect` 与事件边界

- 用于：订阅与退订、定时器、浏览器 API、必要的外部副作用
- 不要用于：同步本可派生的数据、把 props 复制进 state、让多个冗余状态勉强一致、用副作用修补边界设计问题
- 如果一个 effect 只是“当 A 变了就 setState(B)”，优先回到派生逻辑或事件处理函数

## `memo` / `useMemo` / `useCallback`

- 默认不要把 `React.memo`、`useMemo`、`useCallback` 当成起手式
- 只有热点明确、引用稳定性真的重要、结构已经收敛时再考虑
- 改后要能说清：谁是热点、为什么值、证据是什么

## Next.js 边界

- 不需要交互、浏览器 API 或客户端状态时，优先保持服务端边界
- 只有明确需要客户端能力时，再引入客户端边界
- `use client` 应该是有原因的决定，不是默认起手式
- 传给客户端的字段尽量最小化，不要把大对象和重转换结果整包下发
- 重数据获取和重整形优先留在更接近服务端拥有者的位置

## hydration / loading / bundle 观察点

- hydration 前后是否在显示两套不一致状态
- 是否把低频重组件过早打进首屏 bundle
- loading 边界是否真的缩短了等待感，还是只是把阻塞换了位置
- 是否把本可延后加载的图表、编辑器、分析脚本提早放进关键路径

## React / Next.js 任务的最小收口

- 当前问题首先更像等待链、边界、payload、状态设计，还是局部渲染
- 你建议先改哪一层，为什么
- 需要什么证据才能把推断升级成结论
- 哪些局部技巧暂时不建议先上

## 常见红旗

- 独立请求被写成层层串行等待
- 服务端数据和客户端交互混成一团
- route 级或大块页面默认 `use client`
- 把大对象或重转换结果整包传给客户端
- 用户动作被建模成 state + effect 链
- hydration 后出现主题、文案、布局闪烁
- 大量不稳定引用层层下传
- 用 `div` 假装按钮
- 只处理点击，不处理键盘和焦点
- 把“符合框架习惯”直接写成“已经最优”
