# 评审、重构与调试

这份文件用于前端任务中的高风险判断场景：评审、重构与调试。

它们的共同点不是“都不写新功能”，而是都要求更强的证据意识、更强的结构判断、更强的不确定性管理。不要把这三类任务做成泛泛建议、风格点评或自信猜测。

## 总原则

在评审、重构与调试场景中，默认遵守以下原则：

- 先证据，后判断
- 先结构，后表象
- 先风险，后措辞
- 先收敛边界，后扩大改动
- 先说明不确定性，后给建议

这三类任务都不允许用“看起来应该是”“大概没问题”替代工程判断。

## 评审模式

评审的主交付物是问题、风险、回归点和缺口，而不是“整体还不错”的印象。

### 输出顺序

默认按以下顺序输出：

1. 发现的问题
2. 严重度排序
3. 关键依据
4. 开放问题或不确定点
5. 简短总结

如果没有明确问题，也要明确写出“未发现明确问题”，并补充残余风险与验证缺口。

### 严重度判断

评审时，优先识别以下高优先级问题：

- 明确的行为错误或潜在回归
- 结构混乱导致的高维护成本
- 冗余状态或多事实源
- `useEffect` 同步本可派生的数据
- 复杂度堆叠和包装层蔓延
- 缺少空态、加载态、错误态或部分完成态
- 性能结论无证据
- 可访问性明显缺失
- 验证不足却给出强结论

这些都应视为真实问题，而不是“代码风格建议”。

### 评审时要特别看什么

优先检查：

- 输入输出与状态边界是否清楚
- 组件、hook、helper 是否职责过多
- 抽象是否真的降低了复杂度
- 逻辑是否靠近真正拥有它的边界
- 是否有补丁叠补丁的迹象
- 是否把结构问题伪装成性能问题
- 是否遗漏关键用户状态处理
- 是否存在未披露的未执行项与验证缺口

### 评审时不要做什么

不要：

- 用泛泛赞美稀释问题
- 把复杂度问题降级成“可选优化”
- 把明显风险埋到总结后面
- 在没有证据时写成“应该没问题”
- 把“项目一直这样写”当成质量豁免

## 重构模式

重构的目标是降低复杂度、收紧边界、减少部件数量，而不是把原有复杂度重新包装成“更整齐”的形式。

### 重构前先确认

在开始重构前，先明确：

- 哪些行为必须保持不变
- 哪些行为变化是有意的
- 哪些复杂度属于历史债务
- 哪些旧路径可以安全删除
- 回滚边界在哪里

没有这些边界时，不要把大范围结构变动叫做“安全重构”。

### 推荐重构顺序

优先按以下顺序推进：

1. 锁定单一事实源
2. 删掉冗余状态与重复转换
3. 剥离错位副作用
4. 澄清组件 / 模块所有权
5. 删掉不再需要的旧路径
6. 最后再判断是否需要抽象

不要一上来就：

- 抽通用 hook
- 搭大配置对象
- 重新包一层 helper
- 用目录调整冒充结构优化

### 什么不算成功重构

以下情况不应被描述为重构成功：

- 复杂度只是搬了位置
- 新旧路径同时存在却没有退出计划
- 组件更“整齐”了，但边界仍然混乱
- 行为变化存在却没有明说
- 回滚比之前更难

### 重构输出义务

最终说明里至少要说清楚：

- 删掉了哪些旧路径
- 减少了哪些状态、分支、组件责任或包装层
- 哪些行为保证保持不变
- 哪些行为有意变化
- 哪些复杂度暂时保留
- 回滚边界是什么

## 调试模式

调试的目标是定位根因或给出可信的修复路径，而不是写出一串“最像答案”的猜测。

### 调试时先分层

先明确区分：

- 现象
- 证据
- 假设
- 已验证根因
- 未验证推断

没有证据支持的内容，不要写成已确认根因。

### 调试顺序

推荐顺序：

1. 确认现象和影响范围
2. 检查日志、报错、重现条件是否可信且完整
3. 缩小最小可重现边界
4. 判断问题更像状态、渲染、副作用、交互还是性能问题
5. 验证根因
6. 区分临时止血方案与正确修复方案

### 调试时要特别警惕

尤其警惕以下误判：

- 把偶发症状误当稳定重现
- 把日志片段误当完整证据
- 把框架行为误当业务 bug
- 把结构问题误写成单点修复问题
- 在根因未证实时直接给出唯一答案

### 调试输出义务

最终说明里至少要交代：

- 观察到的现象
- 已掌握的证据
- 根因是已确认还是仍推断
- 修复是已验证还是仅建议
- 如果只是止血，必须明确标注为临时方案
- 还缺哪些信息才能收敛到确定结论

## 三类任务共同的红线

以下行为在评审、重构、调试中都应避免：

- 用强语气掩盖不确定性
- 把结构问题降格为审美问题
- 把经验判断写成既成事实
- 为了“显得有结论”而忽略证据不足
- 在不理解边界时给出大范围修改建议

## 推荐表达风格

保持以下风格：

- 直接，但不武断
- 严格，但不表演式苛刻
- 结论清楚，但明确区分已验证与推断
- 优先指出真正影响质量和风险的点

目标不是显得挑剔，而是帮助前端系统变得更简单、更安全、更可维护。
