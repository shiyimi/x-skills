# 评审、重构与调试

在评审、重构和调试这三类高风险场景中读取本文件。

它们共同要求更强的证据意识、结构判断和不确定性管理。不要把这三类任务做成泛泛建议、风格点评或自信猜测。

## 通用原则

- 先证据，后判断
- 先结构，后表象
- 先风险，后措辞
- 先收边界，后扩大改动
- 先说明不确定性，再给结论

## 三种模式的主交付物

| 模式 | 主交付物 | 默认顺序 | 高优先级关注点 |
| --- | --- | --- | --- |
| 评审 | 问题、风险、缺口 | 发现 -> 严重度 -> 依据 -> 不确定点 | 行为错误、结构问题、状态冗余、缺失用户状态、验证不足 |
| 重构 | 降复杂度、收边界、删旧路径 | 锁定边界 -> 删冗余 -> 剥副作用 -> 清所有权 -> 删旧路径 | 单一事实源、旧路径退出、行为保持、回滚可控 |
| 调试 | 根因或可信修复路径 | 现象 -> 证据 -> 假设 -> 验证 -> 修复路径 | 现象和假设分离、最小重现边界、根因是否已验证 |

## 评审规则

评审时应把这些问题视为真实问题，而不是“风格建议”：

- 明确行为错误或潜在回归
- 结构混乱带来的高维护成本
- 冗余状态或多事实源
- `useEffect` 同步本可派生的数据
- 缺少空态、加载态、错误态或部分完成态
- 性能结论无证据
- 可访问性明显缺失
- 验证不足却给出强结论

不要用泛泛赞美稀释问题，也不要把明显风险埋到总结后面。

## 重构规则

重构前先明确：

- 哪些行为必须保持不变
- 哪些变化是有意的
- 哪些旧路径可以安全删除
- 回滚边界在哪里

以下情况不算重构成功：

- 复杂度只是搬了位置
- 新旧路径同时存在却没有退出计划
- 组件更整齐了，但边界仍然混乱
- 行为变化存在却没有明说

## 调试规则

调试时必须区分：

- 现象
- 证据
- 假设
- 已验证根因
- 未验证推断

尤其警惕：

- 把偶发症状误当稳定重现
- 把日志片段误当完整证据
- 在根因未证实时直接给唯一答案
- 把结构问题误写成单点修复问题

## 共同红线

以下行为在三类任务里都应避免：

- 用强语气掩盖不确定性
- 把结构问题降格为审美问题
- 把经验判断写成既成事实
- 为了显得有结论而忽略证据不足

## 输出义务

最终应至少交代：

- 已验证事实是什么
- 哪些仍是推断
- 风险或问题按什么优先级处理
- 如果给出改动建议，回滚边界在哪里
