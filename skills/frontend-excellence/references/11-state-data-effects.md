# 状态、数据与副作用

在处理状态建模、异步流、表单或 effect 时读取本文件。

前端复杂度最常见的根源，不是 UI 本身，而是事实源重复、派生值被存起来，以及 effect 变成状态同步器。

## 默认顺序

先判断一个事实本来属于哪一类：

1. 服务端状态
2. 本地状态
3. URL 状态
4. 全局状态

不要上来就把一切塞进本地 state 或全局 store。

## 单一事实源

每个业务事实尽量只保留一个事实源。

优先避免：

- 同一信息在多个 state 中存多份
- props 和本地 state 各维护一套
- 计算结果被缓存成长期状态
- URL、组件状态、全局状态同时表达同一语义

如果一个事实需要“保持同步”，先怀疑是不是本来就不该存两份。

## 派生优于存储

只要一个值可以稳定推导出来，就优先派生，不要额外存状态。

高风险信号：

- `setState` 只是为了缓存计算结果
- `useEffect` 里把 A 同步到 B
- 多个布尔值共同表达一个更高层状态

## 副作用边界

`effect` 应主要用于与 React 外部世界同步，例如：

- 订阅与退订
- 浏览器 API
- 定时器
- 必要的外部同步

以下通常属于误用：

- 同步本可派生的数据
- 用 effect 串联多个状态保持一致
- 以副作用修补所有权设计问题
- 用 effect 驱动正常渲染逻辑

## 异步流与表单

至少回答这些问题：

- 加载、成功、失败、部分完成分别如何表达
- 何时需要重试、刷新或失效
- 字段值、校验、服务端错误分别归谁拥有
- 提交中、成功、失败如何反馈

不要只处理 happy path。

## 数据整形位置

优先在接近数据拥有者的位置完成关键整形，并给复杂转换命名。

避免：

- 在 render 中内联做大量转换
- 相同转换散在多个分支
- 让 JSX 承担过多数据整理工作

## 红旗

看到这些现象时，应优先怀疑状态设计有问题：

- 同一事实多处维护
- 派生值被存状态
- effect 专门负责同步状态
- 状态更新顺序影响业务正确性
- 表单、请求和展示状态缠在一起

## 输出义务

如果本轮涉及状态或副作用调整，最终应说清楚：

- 哪个事实源被收敛成单一来源
- 删除了哪些冗余状态或同步逻辑
- 哪些 effect 被删掉、保留或改写
- 异步流和用户状态如何被重新表达
- 还保留哪些状态复杂度，以及为什么
