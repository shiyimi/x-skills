# 状态、数据与副作用

这份文件负责状态建模、数据流、派生逻辑、副作用和表单 / 异步交互中的边界控制。

前端复杂度里最常见、最顽固的一部分，往往不是 UI 本身，而是状态和副作用失控。状态一旦冗余、错位或同步关系混乱，组件结构、性能和可测试性都会迅速恶化。

## 状态优先级

默认按以下顺序理解状态：

- 服务端状态
- 本地状态
- URL 状态
- 全局状态

先判断“这个事实本来属于哪一类”，再决定放哪，不要上来就把一切都塞进本地 state 或全局 store。

## 单一事实源

每个业务事实尽量只有一个事实源。

优先避免：

- 同一信息在多个 state 中存多份
- props 和本地 state 各自维护一套
- 计算结果被缓存成长期状态
- URL、组件状态、全局状态同时维护同一语义

一旦一个事实需要“保持同步”，先问：是不是本来就不该存两份。

## 派生优于存储

只要一个值可以从已有状态、参数或数据稳定推导出来，就优先用派生逻辑，不要额外存起来。

应该谨慎的典型信号：

- `setState` 只是为了缓存计算结果
- `useEffect` 里把 A 改动同步到 B
- 多个布尔值共同表达一个更高层状态

如果一个值存在是为了方便渲染，不代表它一定应该被存成状态。

## 状态归属

状态应该放在真正需要拥有它的最小边界中。

优先：

- 局部状态留在局部组件
- 多个兄弟组件共享的状态提升到最近公共拥有者
- 与路由强绑定的状态放进 URL 语义
- 明确的跨区域共享事实再考虑全局状态

避免：

- 因为“以后可能用到”就把局部状态提前提升
- 因为传 props 麻烦就直接全局化
- 因为当前组件太大就继续塞更多状态进去

## 副作用边界

副作用是同步 React 之外世界的机制，不是修补状态设计的万能胶。

副作用常见合法场景：

- 订阅与退订
- 浏览器 API
- 定时器
- 必要的外部同步

副作用常见误用：

- 同步本可派生的数据
- 在 effect 中串联多个状态保持一致
- 用 effect 掩盖所有权设计问题
- 通过 effect 驱动正常渲染逻辑

只要一个 effect 看起来像“状态同步器”，就应该高度警惕。

## 异步流与数据获取

异步数据流至少要回答这些问题：

- 数据来自哪里
- 加载中怎么表达
- 成功后怎么表达
- 失败后怎么表达
- 部分成功或局部失败怎么表达
- 何时需要重试、刷新或失效

不要只处理“请求成功后展示结果”这一条 happy path。

## 表单状态

表单最容易掉进“局部方便、整体混乱”的陷阱。

优先明确：

- 字段值归谁拥有
- 校验在何时触发
- 错误提示何时出现
- 提交中、提交成功、提交失败如何反馈
- 初始值与脏数据如何区分

避免：

- 字段值、派生错误和服务端错误全部混在一个扁平状态里
- 用 effect 修补表单同步
- 一边从 props 读值，一边在本地重存一份却不解释原因

## 数据整形与渲染分离

数据整形逻辑不要随意散落在 render 分支里。

优先：

- 在接近数据拥有者的位置完成关键整形
- 给复杂转换命名
- 让渲染层消费更稳定、更可读的数据形态

避免：

- 每次 render 都内联做大量转换
- 相同转换逻辑散在多个分支中
- 让 JSX 承担过多数据整理工作

## 状态层常见问题清单

一旦看到以下现象，应优先怀疑状态设计有问题：

- 同一事实多处维护
- 派生值被存状态
- effect 专门负责同步状态
- 状态更新顺序影响业务正确性
- 多个布尔值拼出一个阶段状态
- 表单、请求和展示状态缠在一起

这些问题不解决，继续往上写功能，只会把复杂度锁死。

## 输出时应说明什么

如果本轮工作涉及状态或副作用调整，最终说明尽量明确：

- 哪个事实源被收敛成了单一来源
- 删除了哪些冗余状态或同步逻辑
- 哪些 effect 被删掉、保留或重写
- 异步流和用户状态如何被重新表达
- 还存在哪些无法立刻消除的状态复杂度
