# 质量门禁

在把任务表述为“已完成”“已修复”“已优化”“已通过”之前，必须通过与风险匹配的质量门禁。

这些门禁的目的不是增加仪式感，而是阻止以下问题：

- 假完成
- 用补丁掩盖结构问题
- 只处理 happy path
- 用强烈措辞掩盖未验证事实
- 把风险藏在看似自信的结论后面

## 宣称完成前的基础要求

在声称成功之前，至少要做到：

- 已完成与任务风险匹配的验证
- 已区分事实、推断与猜测
- 已披露未执行项
- 已说明残余风险与不确定性

没有验证时，不要写成“已验证”。只有局部证据时，不要写成“整体已通过”。

## 结构门禁

检查当前结果是否在结构上成立，而不是仅仅能运行。

至少回答：

- 结果是否比之前更简单、更清晰或边界更明确
- 是否删除了可删的重复状态、重复转换、重复分支
- 逻辑是否回到了真正拥有它的组件或模块附近
- 是否新增了本可避免的抽象
- 是否用兼容层继续扩散旧债务
- 副作用、渲染、数据整形是否仍然混在一起

如果任务“能用”，但只能靠结构更混乱来成立，则此门禁不通过。

## 体验门禁

检查用户真实会遇到的状态是否被负责地处理。

当任务相关时，至少确认：

- 空态已处理
- 加载态已处理
- 错误态已处理
- 部分完成态 / 降级态已处理
- 异步过程有足够反馈
- 交互流程可理解
- 键盘可达性和焦点行为没有明显破坏
- 语义结构基本成立
- 桌面端与移动端都被最低限度地考虑过

不要因为“这次主要改的是逻辑”就跳过这些用户层面的责任。

## 性能门禁

检查性能结论是否真实，或改动是否意外引入了额外性能成本。

至少回答：

- 这次优化是否基于证据、明确瓶颈或具体风险
- 是否只是用性能技巧掩盖结构问题
- 是否引入了不必要的 render churn、重复计算或不稳定引用
- 如果没有做性能验证，是否已明确说明

把“我感觉会更快”写成“已优化”是不通过的。

## 验证门禁

检查执行真实性与验证充分性。

至少回答：

- 实际运行了什么
- 没有运行什么
- 语法、类型、内容一致性、手动检查是否做到与风险匹配的程度
- “已修复”“无回归”“已优化”等结论是否有对应证据
- 必要前提和环境假设是否说清楚

不要用自信措辞替代执行证据。

## 风险与回滚门禁

检查这次改动是否可控。

至少回答：

- 影响面是什么
- 还有什么可能失败
- 哪些假设尚未被证实
- 回滚路径是否清楚
- 回滚边界是否足够局部、足够易懂

如果回滚说明都说不清，这次改动就不该被描述为低风险。

## 评审场景补充门禁

当前任务是评审时，还应额外确认：

- 发现的问题按严重度排序
- 结构问题被视为真实问题，而不是“风格建议”
- 缺少状态处理、缺少验证、复杂度堆叠被明确指出
- 结论足够具体，可以直接行动

不要把真正的问题淹没在泛泛总结里。

## 重构场景补充门禁

当前任务是重构时，还应额外确认：

- 移动部件数量是否真的减少
- 所有权边界是否更清楚
- 行为是否保持一致，若不一致是否明确说明
- 是否在安全前提下删掉了旧路径，而不是只叠加新路径
- 回滚点是否仍然清楚

不要把“把复杂度搬家”叫做重构成功。

## 调试场景补充门禁

当前任务是调试时，还应额外确认：

- 现象与假设是否分开表述
- 根因是已验证还是仍在推断
- 日志、症状、重现步骤是否被批判性使用
- 修复是已验证还是仅提出方案

不要把猜测包装成已确认诊断。

## 不通过条件

出现以下任一情况时，不应宣称任务已完成：

- 结构明显更乱了
- 结果依赖补丁叠补丁
- 只处理了 happy path
- 性能结论没有证据
- 跳过验证却不披露
- 明显忽视了可访问性或响应式
- 回滚边界不清楚
- 用自信措辞掩盖残余风险

此时应坦诚说明缺口，并明确后续需要补什么。
