# 评审检查清单：按四原则扫查

按 Karpathy 四原则扫查改动，识别违背信号。

---

## Think Before Coding 检查清单

**目标：发现隐藏假设、未解决困惑、缺失权衡。**

### 隐藏假设扫查

```markdown
✅ 检查点：
- [ ] 数据存在性假设是否明确
  → userId、data、config 等是否假设存在
- [ ] 外部状态假设是否明确
  → 服务可用、网络正常、缓存有效
- [ ] 并发假设是否明确
  → 无竞态、顺序执行、单线程
- [ ] 时间假设是否明确
  → 时区、时间格式、超时约定

❌ 隐藏假设信号：
- 直接使用参数未检查存在性
- 外部调用未处理失败场景
- 共享状态未考虑并发
- 时间处理未考虑时区差异
```

### 未解决困惑扫查

```markdown
✅ 检查点：
- [ ] 不理解的代码是否被修改或删除
- [ ] 不确定的逻辑是否有注释标注
- [ ] 不清楚的边界是否有明确处理
- [ ] 不理解的设计是否有询问记录

❌ 未解决困惑信号：
- 修改或删除了不理解但有价值的注释
- 复杂逻辑无解释但改动者可能不理解
- 边界条件未处理但改动者可能不清楚需求
```

### 权衡分析扫查

```markdown
✅ 检查点：
- [ ] 是否呈现多个方案选择
- [ ] 是否说明为何选择此方案
- [ ] 是否说明替代方案的权衡
- [ ] 是否说明此方案的代价

❌ 权衡缺失信号：
- 引入重要依赖或架构变更但未说明选择理由
- 存在明显替代方案但未提及
- 方案有明显代价但未说明
```

## Simplicity First 检查清单

**目标：发现过度工程、臃肿抽象、推测性设计。**

### 过度工程扫查

```markdown
✅ 检查点：
- [ ] 解决方案是否比问题更简单
- [ ] 代码行数是否与问题规模匹配
- [ ] 是否有比直接实现更复杂的方案
- [ ] 是否有"Would a senior engineer say this is overcomplicated?"

❌ 过度工程信号：
- 1000 行代码做 100 行能做的事
- 解决方案比问题描述更复杂
- 引入复杂模式解决简单问题
- 抽象层超过必要数量

判断标准：
"代码行数远超问题规模" → 🟡 Recommended
"复杂度导致无法验证行为" → 🔴 Blocking
```

### 臃肿抽象扫查

```markdown
✅ 检查点：
- [ ] 抽象是否有多个使用者
- [ ] 抽象是否比实现更简单
- [ ] 抽象是否解决真实问题
- [ ] 抽象是否覆盖实际场景

❌ 臃肿抽象信号：
- 抽象只有单一使用者
- 抽象比直接实现更复杂
- 抽象覆盖假设而非实际场景
- 抽象增加理解成本而非降低

判断标准：
"抽象只有单一使用者" → 🟡 Recommended
"抽象掩盖核心逻辑导致无法验证" → 🔴 Blocking
```

### 推测性设计扫查

```markdown
✅ 检查点：
- [ ] 是否有未请求的功能
- [ ] 是否有未请求的配置选项
- [ ] 是否有未请求的扩展点
- [ ] 是否有"未来可能需要"的设计

❌ 推测性设计信号：
- 添加了未请求的功能或配置
- 为假设场景设计扩展点
- "为了未来扩展"但无实际需求
- 配置性超出实际使用场景

判断标准：
"添加未请求的功能" → 🟡 Recommended
```

---

## Surgical Changes 检查清单

**目标：发现越界改动、删除不理解代码、风格不匹配。**

### 越界改动扫查

```markdown
✅ 检查点：
- [ ] 每个改动是否追溯到用户请求
- [ ] 是否改动了与任务无关的文件
- [ ] 是否改动了与任务无关的代码区域
- [ ] 是否有"顺便改进"的改动

❌ 越界改动信号：
- 改动无法追溯到请求
- 改动了与任务无关的文件
- "顺便重构"或"顺便优化"相邻代码

判断标准：
"Every changed line should trace directly to the user's request."
无法追溯 → 🟡 Recommended
导致行为变化 → 🔴 Blocking

✅ 允许清理：
- YOUR changes 导致的 orphan imports/variables
- YOUR changes 导致的 unused code

❌ 不允许删除：
- 预存在的死代码
- 不理解的注释或代码
```

### 删除不理解代码扫查

```markdown
✅ 检查点：
- [ ] 是否删除了注释但不确定其价值
- [ ] 是否删除了代码但不理解其用途
- [ ] 是否修改了代码但不理解其边界
- [ ] 是否简化了逻辑但不理解其设计意图

❌ 删除不理解信号：
- 删除了有价值注释（如 TODO、边界说明）
- 删除了代码但可能影响边界场景
- 简化了逻辑但丢失了重要设计

判断标准：
"删除不理解的注释/代码" → 🔴 Blocking
```

### 风格不匹配扫查

```markdown
✅ 检查点：
- [ ] 新增代码是否匹配现有命名风格
- [ ] 新增代码是否匹配现有组织风格
- [ ] 新增代码是否匹配现有格式风格
- [ ] 新增代码是否匹配现有 API 风格

❌ 风格不匹配信号：
- 命名风格与项目不一致
- 文件组织方式与众不同
- 格式与项目不一致

判断标准：
"风格不一致" → 🟡 Recommended
```

## Goal-Driven Execution 检查清单

**目标：发现无验证、无成功标准、无计划。**

### 验证扫查

```markdown
✅ 检查点：
- [ ] 是否有测试覆盖关键路径
- [ ] 是否有测试覆盖边界场景
- [ ] 是否有手动验证证据
- [ ] 是否有验证结果陈述

❌ 无验证信号：
- 宣称完成但无测试或验证证据
- 改动核心逻辑但无测试覆盖
- 改动边界处理但无边界测试

判断标准：
"宣称完成但无验证" → 🟡 Recommended
```

### 成功标准扫查

```markdown
✅ 检查点：
- [ ] 是否有明确的成功标准
- [ ] 是否有可验证的完成定义
- [ ] 是否有自动化验证机会
- [ ] 是否有验证循环机会

❌ 无成功标准信号：
- "完成"定义模糊
- 无法判断是否真正完成
- 手动验证可以自动化

判断标准：
"成功标准缺失" → 🔵 Optional
"可自动化但手动验证" → 🔵 Optional
```

### 计划扫查（多步骤任务）

```markdown
✅ 检查点：
- [ ] 是否有明确的步骤陈述
- [ ] 是否有每个步骤的验证点
- [ ] 是否有 `[Step] → verify: [check]` 结构
- [ ] 是否有步骤间的依赖说明

❌ 无计划信号：
- 多步骤任务无步骤陈述
- 无验证点或验证不明确
- 步骤依赖不清晰

判断标准：
"多步骤任务无计划" → 🟡 Recommended
```

---

## 快速扫查流程

```markdown
对每个改动文件：

Step 1: Think Before Coding 扫查（1-2 分钟）
   → 快速识别：隐藏假设、不理解的改动、重要选择

Step 2: Simplicity First 扫查（2-3 分钟）
   → 评估：代码规模 vs 问题规模、抽象数量、未请求功能

Step 3: Surgical Changes 扫查（1-2 分钟）
   → 检查：改动是否可追溯、是否有删除不理解代码

Step 4: Goal-Driven Execution 扫查（1 分钟）
   → 确认：是否有验证、是否有多步骤计划
```

---

## 改动规模策略

| 改动规模 | 扫查策略 |
|---------|---------|
| < 50 行 | 快速 Step 1-3，Step 4 次要 |
| 50-200 行 | 按四原则完整扫查 |
| 200-500 行 | 重点 Step 1-2，Step 3-4 标记可疑点 |
| > 500 行 | 建议 PR 拆分，或分段扫查 |

---

## 时间分配

| 原则 | 建议时间占比 |
|-----|-------------|
| Think Before Coding | 30% |
| Simplicity First | 40% |
| Surgical Changes | 20% |
| Goal-Driven Execution | 10% |

时间紧张时，优先保证 Think Before Coding 和 Simplicity First 的扫查质量。
