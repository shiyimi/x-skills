# 工作日志编辑

把口语化、流水账式的日常工作记录，重组为专业、精炼、可追溯、可分析的标准化工作日志，使其能同时支撑团队信息同步、可复用经验沉淀，以及人员分析、过程复盘和绩效评估。

## 先理解：这是一次"事实重组"，不是创作

这条日志最终会进入团队同步、复盘和绩效评估——它既是信息载体，也是证据。所以本 skill 的底层原则只有一条：

**只对口语化表达做结构重组和语意精炼，绝不篡改或添加任何原文没提到的事实、数据、人员或时间。**

这条原则决定了后面所有规则的分寸：
- 模糊的，改清晰（改的是表达，不是事实）；
- 缺失的，标"待确认"（不是补一个看起来合理的）；
- 低价值的，删除（删的是噪声，不是事实）；
- 有风险的，亮出来（不隐藏，也不夸大）。

拿不准时，宁可保留原文表述并标注待确认，也不要为了"显得专业"而拔高或脑补。

## 适用 / 不适用

适用于：把**已经存在的**口语化、流水账式日常工作记录（个人日报、周报、站会发言转写、零散工作汇报）改写成标准化日志。

不适用于：从零起草一篇全新的日志、写会议纪要、写周报 PPT、写正式汇报材料、或对非工作类文本做通用润色。这些是别的体裁，不要套用本 skill 的单段格式。

## 输出硬约束（不可让步）

这一节是本 skill 与普通润色的根本区别，必须逐字遵守：

1. **输出必须是一整段话。** 严禁任何标题、序号、列表、换行符。整条日志从头到尾只有一段纯文本。
2. **多个独立事务之间，一律用中文分号"；"分隔**，最后一个事务用句号"。"结尾。
3. **每个事务按固定结构组织**，顺序为：
   `【项目/系统/模块/功能】 + 具体动作 + 核心对象 + 当前进展/结论 + 后续动作/卡点/风险/经验（原文有才写）`
4. **开头尽量明确项目/系统/模块/功能名称**，用方括号包住；原文实在判断不出归属的，写 `【待确认模块】`，不要瞎编一个模块名。

为什么是单段、为什么用分号：工作日志是紧凑的流水记录，不是清单或待办。单段 + 分号既能强迫每一句都承载信息（挤掉水分），又能让每个事务保持原子、可扫读，整段读下来就是"今天这个模块发生了这些事"的一个完整交代。方括号里的模块名是这条日志的索引键——没有它，日志就没办法按项目/模块聚合、检索和分析。

> 若输入同时含**多人或多日**的记录，按人或按日各成一段（段与段之间可换行），但**每一段内部仍严格遵守单段规则**。单人单日的常规输入就是一整段。

## 处理流程

收到一条流水账记录后，按以下顺序处理：

1. **拆事务**：把整段流水账切成一个个独立事务。判断标准是"这是不是一件可以单独说清楚的事"。
2. **判价值**：对每个事务先问"它有没有结论、决定、风险、待办或产出"。纯粹的会议/沟通/学习/演示/对接流水账，如果没有这些，就是低价值噪声，直接删（见下"低价值内容"）。注意：删的是"没有信息量的活动描述"，不是删事实——一个有结论或带卡点的会议要保留，只删"开了个会"本身。
3. **改动作**：把模糊动词换成可核实的事实动词（见下"动词处理"）。动词必须贴合原文事实，不能为了显得专业而拔高（原文只是"看了一眼"，不能写成"深入评审"）。
4. **写进展**：写清"做到哪一步"。已完成说清完成对象；未完成说清当前阶段；有结论写结论；有待办写下步动作。
5. **标风险/经验**：有阻塞/依赖/隐患的亮成卡点；有已验证做法或可复用结论的，写成"可复用"或"建议…"。
6. **串段**：把保留下来的事务按模块归位、用分号串成一整段，句末句号。
7. **自检**：用下面的清单过一遍再输出。

## 规则细则

### 动词处理

删掉"看了下、弄了下、搞了下、搞了搞、处理了下、沟通了、参加了、学习了、跟进了、弄了一下"这类**无法核实、可大可小**的模糊活动词。它们是流水账最大的噪声来源——"看了下"可能瞄一眼，也可能通读三遍，谁也说不清。

换成**可核实、有边界**的事实动词：完成、补充、修复、验证、确认、拆分、提交、回写、评审、退回、定位、复现、整理、形成结论、发布、对接、梳理……

把握的原则比记词表更重要：**用能被"做没做到、做到哪了"检验的动词，不用只描述活动本身的动词。** "处理了登录问题"无法检验；"定位到登录空指针并提交修复"可以检验。只要守住这条原则，遇到词表外的词也能正确改写。

#### 高价值工程词汇（体现专业度，但严禁拔高）

很多真实工作本身是有工程深度的，用对词能让日志准确呈现其价值——这对绩效与复盘场景很重要。但这类词也是拔高事故的高发区：原文只是改了点小东西，若滥用"架构/优化/重构"，日志就失真了。所以核心是"**原文确有此事实才能用，且必须带具体落点**"。

按类型使用（仅当原文事实匹配时）：

| 类型 | 可用词汇 | 使用前提（必须同时满足） |
| --- | --- | --- |
| 架构 / 边界 | 架构设计、架构调整、分层、边界划分、领域建模 | 原文确有结构层面的设计/调整动作 |
| 组件 / 抽象 | 组件化、组件抽取、组件复用、抽象、封装、解耦、模块化 | 原文确有抽取/封装/复用的具体动作 |
| 质量 / 性能 | 重构、优化、精简、提效、性能优化 | 必须指明优化对象与方向（如响应耗时、包体积、渲染帧率） |
| 发布 / 运维 | 迁移、灰度、回滚、压测、监控接入、治理 | 原文确有相应发布/运维动作 |

防拔高对照（左 ❌ 是拔高、禁止；右 ✅ 才是诚实呈现）：

- ❌ 优化了下登录 → ✅ **仅当原文确有性能动作时**写"优化登录接口响应耗时"；否则只是"修复登录 Bug"。
- ❌ 调整了下架构 → ✅ **仅当原文确有架构动作时**写"拆分订单与支付边界"；否则属过度拔高。
- ❌ 重构了下代码 → ✅ **仅当原文确有结构调整时**写"将 Report 组件拆分为容器 + 展示组件"。
- ❌ 做了个组件 → ✅ "抽取 XX 公共组件并复用于 N 处"（要有复用事实）。

判断口诀：**每用一个高价值词，都要能回答"具体动作落到了什么对象上、有没有可核实的依据"。答不上来就降级用中性事实动词——宁可平淡，不可虚高。** 一条准确但平淡的日志，远胜于一条华丽但失真的日志。

### 进展要求

- 已完成：说清**完成了什么对象**（"修复了登录模块空指针"），不是"搞定了"。
- 未完成：说清**当前阶段**（"已复现，待定位根因"），不是"在做"。
- 有结论：直接写结论（"结论：方案 A，工期偏紧"）。
- 有待办：写**下一步具体动作**（"下一步：周二前出接口文档"），不是"后续跟进"。
- 会议/对接/评审/学习/演示类：**只保留**结论、决定、风险、待办或产出；活动本身不保留。
- 原文有这事、但没写结论、而团队又需要知道的，标 `（待确认：结论/待办）`，不要替它编一个结论。

### 风险要求

风险是工作日志里**单位价值最高**的信息——一个被埋住的卡点会让整个团队误判进度。所以：

- 原文明确有阻塞、延期、依赖、质量隐患、需求不清、环境问题、人员协作问题的，必须写清，用"目前卡在……，需……支持"或"后续需关注……"。
- 原文出现"没法推进、在等、依赖别人、又报错了、反复失败"这类信号、但没明说风险时，按"疑似卡点"标注并**保留原文描述**，例如 `（疑似卡点：回调反复失败，原文未说明原因）`。
- 两条底线：**不隐藏风险**（不能把卡点写成正常进展），**也不夸大风险**（不能把"在等回复"写成"严重阻塞"）。

### 经验建议

只保留**已验证的做法、明确的建议、可复用的结论**，写成"可复用：……"或"建议……"。不要写"本次收获很大""学到了很多"这种空泛总结——那是噪声。没有可复用结论就不要硬凑。

### 低价值内容处理

会议、沟通、学习、演示、对接类记录，**只保留**其中的结论、决定、风险、待办或产出。

既没有结论、也没有待办、又没有管理价值的内容，**直接删除**。例如"晚上回去研究了下 react 并发模式，感觉有点意思"——没有结论、没有待办、不影响团队——删掉。这不是删事实，而是这条记录里根本没有可沉淀的事实。

### 关键信息缺失

若关键信息（模块、对象、进展、结论等）严重缺失而无法准确改写，保留 `（待确认：[具体缺什么]）`。这是对绩效与复盘场景的诚实，比一个看似完整实则编造的日志有价值得多。

## 输出前自检

输出前，对保留下来的**每个事务**问一遍：

- 做了什么？（动作 + 对象，且动词可核实）
- 做到哪一步？（进展/阶段明确）
- 结论是什么？（有则写，无则待确认）
- 是否有卡点？（有则亮出，不隐藏）
- 下一步是什么？（有待办则写具体动作）

回答不了的，不要硬写——按"待确认"标注，或按低价值删除。

最后再确认一次整体格式：**一整段、无标题/序号/列表/换行、事务间分号、句末句号、每段以【模块】开头**。

## 示例（紧凑版）

更多场景的 before/after 见 `references/examples.md`（含 bug 卡点、需求评审、低价值删除、信息缺失待确认、可复用经验等多种情况）。

**输入**（流水账）：
> 今天上午看了下登录那个 bug，好像是个空指针，弄了下没搞定，下午开了个会讨论下个版本排期，产品说要加个积分商城，我们觉得工期有点紧，晚上回去研究了下 react 的并发模式，感觉有点意思。另外之前那个支付掉单的问题我跟进了一下，客服又反馈了两单，应该还是回调那边的问题。

**输出**（标准化日志）：
> 【登录模块】定位空指针类型 Bug，当前未修复（疑似卡点：暂未解决，需进一步排查根因）；【下版本排期】评审积分商城需求，结论为团队判断工期偏紧，后续需关注排期风险；【支付模块】跟进掉单问题，新增 2 单客服反馈，初步判断为回调异常，下一步定位回调链路。

（"研究了下 react 并发模式"因无结论、无待办、无管理价值，已删除。）
