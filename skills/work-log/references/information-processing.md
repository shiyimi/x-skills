# 工作日志信息处理规则

## 核心原则

工作日志处理是事实重组，不是创作。只对口语化表达做结构重组和语意精炼，不得篡改或添加原文未提到的事实、数据、人员或时间。

- 模糊信息改清晰，但不改变事实。
- 缺失信息标记为“待确认”，不得补造。
- 删除没有结论、决定、风险、待办或产出的低价值活动描述。
- 风险必须明确呈现，但不得夸大。

## 适用范围

适用于已经存在的个人日报、周报、站会记录和零散工作汇报。不适用于从零起草日志、会议纪要、周报 PPT、正式汇报材料或非工作文本润色。

## 标准信息格式

1. 单人单日的标准化日志必须是一整段纯文本，不使用标题、序号、列表或换行。
2. 多个独立事务使用中文分号 `；` 分隔，最后一个事务以句号 `。` 结尾。
3. 每个事务使用固定结构：
   `【项目/系统/模块/功能】 + 具体动作 + 核心对象 + 当前进展/结论 + 后续动作/卡点/风险/经验（原文有才写）`
4. 无法判断归属时使用 `【待确认模块】`，不得编造模块名。
5. 输入同时包含多人或多日记录时，按人或按日分别生成一段；每段内部继续遵守单段规则。

## 处理步骤

1. **拆分事务**：将输入拆分成可以独立说明的事务。
2. **判断价值**：保留有结论、决定、风险、待办或产出的事务；删除无信息量的会议、沟通、学习、演示或对接描述。
3. **明确动作**：将“看了下、弄了下、搞了下、处理了下、沟通了、参加了、学习了、跟进了”等模糊活动词改为与原文事实匹配、可核实且有边界的动作。
4. **写明进展**：已完成时说明完成对象；未完成时说明当前阶段；有结论时直接写结论；有待办时写具体下一步。
5. **标记风险和经验**：保留阻塞、延期、依赖、隐患和已验证的可复用结论。
6. **组织标准信息**：按模块归位，用中文分号串联事务，以句号结尾。
7. **自检**：确认每项事实均来自原文，动作可核实，进展明确，风险未隐藏，待办未编造。

## 动词规则

优先使用完成、补充、修复、验证、确认、拆分、提交、回写、评审、退回、定位、复现、整理、形成结论、发布、对接、梳理等事实动词。

高价值工程词汇仅在原文具备对应事实时使用：

| 类型 | 可用词汇 | 使用前提 |
| --- | --- | --- |
| 架构与边界 | 架构设计、架构调整、分层、边界划分、领域建模 | 原文确有结构层面的设计或调整 |
| 组件与抽象 | 组件化、组件抽取、组件复用、抽象、封装、解耦、模块化 | 原文确有抽取、封装或复用动作 |
| 质量与性能 | 重构、优化、精简、提效、性能优化 | 明确指出优化对象和方向 |
| 发布与运维 | 迁移、灰度、回滚、压测、监控接入、治理 | 原文确有对应发布或运维动作 |

每个高价值词都必须能回答“动作落到什么对象、依据是什么”。无法回答时改用中性事实动词。

## 进展、风险与经验

- 已完成：明确完成的对象，不使用“搞定了”。
- 未完成：明确当前阶段，不使用“在做”。
- 有结论：直接写结论。
- 有待办：写具体下一步，不使用“后续跟进”。
- 原文存在事务但缺少团队需要的结论或待办时，标记 `（待确认：结论/待办）`。
- 原文明确出现阻塞、延期、依赖、质量隐患、需求不清、环境问题或协作问题时，写明卡点和所需支持。
- 原文出现“没法推进、在等、依赖别人、反复失败”等信号但未说明原因时，保留原文并标记疑似卡点。
- 仅保留已验证做法、明确建议或可复用结论，不添加空泛总结。

## 关键信息缺失

模块、对象、进展或结论严重缺失时，使用 `（待确认：[具体缺失信息]）`。不得为了形成完整句子而补造事实。

## 输出自检

对每个事务检查：

- 动作和对象是否明确且可核实。
- 当前进展或阶段是否明确。
- 原文有结论时是否已保留。
- 原文有卡点时是否已呈现。
- 原文有下一步时是否已具体表达。
- 是否保持单段、中文分号分隔、句号结尾和 `【模块】` 开头。

更多输入输出场景见 `examples.md`。
