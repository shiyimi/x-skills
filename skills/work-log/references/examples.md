# 工作日志编辑 — 示例库

每条示例展示：流水账输入 → 标准化输出 → 改写要点。所有输出都严格遵守"一整段、无标题/序号/列表/换行、事务间分号、句末句号、以【模块】开头"。

输出与原文之间**只做结构重组与语意精炼，不增删事实**。

---

## 示例 1：bug 卡点 + 低价值删除

**输入**：
> 今天主要在搞登录页那个崩溃，点退出就闪退，复现了好几次，应该是个空指针，但还没找到具体位置，弄了一下午没搞定。中午产品拉了个会同步了下版本的事，也没啥结论。晚上回去看了个 limit order 的文章，感觉有点意思。

**输出**：
> 【登录模块】复现并定位退出闪退 Bug，初步判断为空指针，当前未修复（疑似卡点：下午排查未果，需进一步定位具体代码位置）。

**要点**：
- "搞崩溃"→"复现并定位闪退 Bug"（动作可核实）。
- 反复复现 + 未解决 → 明确标"疑似卡点"并保留原文描述。
- 产品同步会"没啥结论"→ 删除（低价值，无结论无待办）。
- "看了 limit order 文章，有点意思"→ 删除（无结论、无待办、无管理价值）。

---

## 示例 2：需求评审有结论 + 工期风险

**输入**：
> 上午跟产品对了下下个版本的需求，主要是积分商城那块，他们想要排行榜 + 签到，我看了一下工作量比较大，跟他们说了下可能要砍点功能，他们说要再想想。下午就开始画商城首页的草图了，画了个大概。

**输出**：
> 【积分商城模块】对接下版本需求，范围含排行榜与签到，结论为工作量偏大、已建议精简功能，待产品方确认；【积分商城模块-首页】产出首页草图初稿，当前为大致框架，下一步细化。

**要点**：
- "跟产品对了下需求"→"对接需求"并写出**范围、结论、待办**。
- "可能要砍功能"→ 提炼为"已建议精简功能"，作为明确待办。
- "画了个大概"→ 写清当前阶段（大致框架）+ 下一步（细化）。

---

## 示例 3：关键信息缺失（不编造）

**输入**：
> 今天修了个 bug，搞定了，测试那边说没问题了。

**输出**：
> 【待确认模块】修复一例 Bug（待确认：模块/对象、根因、修复内容均缺失），测试侧已验证通过。

**要点**：
- 原文完全没说修的是什么 bug、属于哪个模块。
- 不编造模块和根因；标 `【待确认模块】` 并列出具体缺失项。
- 测试已通过是可保留的事实，写出。

## 示例 4：可复用经验

**输入**：
> 昨天那个导出接口超大数据量会 OOM，今天我换成了流式分批写入，测了下百万级数据也不爆了，已经合到主干上了，让前端那边接一下。

**输出**：
> 【导出接口】修复大数据量导出 OOM，方案为改用流式分批写入（可复用：百万级数据量场景适用流式分批写入规避 OOM），已合并主干并验证，下一步对接前端联调。

**要点**：
- 解决方案明确且经验证 → 提炼为"可复用"经验，供后续同类场景复用。
- 进展写清：已合并主干 + 已验证；下一步写具体动作（前端联调）。

## 示例 5：多人多日（分段，段内仍单段）

**输入**：
> 周一：搞了下报表导出的格式问题，不太对，还没好；看了下 react 性能优化的东西。
> 周二：报表那个格式调好了，已提交；下午开会说了下这周排期，我负责订单模块的重构。

**输出**（按日各一段，段间换行，段内单段）：
> 【报表导出】修复导出格式问题，周一未完成（疑似卡点：格式未达预期，需继续调整）。
>
> 【报表导出】完成导出格式修复并提交代码；【订单模块】承接本周重构任务（结论：本周个人分工为订单模块重构，待确认：具体重构范围与排期）。

**要点**：
- 周一"看了 react 性能优化"→ 删除（低价值）。
- 周一格式"还没好"→ 标疑似卡点。
- 排期只说了"负责订单模块重构"，具体范围没说 → 待确认，不编造。
- 多日输入：按日分段，每段内部仍是单段、分号分隔、句末句号。

## 示例 6：明确阻塞与外部依赖

**输入**：
> 新版支付接了，但是第三方那边的回调地址还没给我，我一直没法测，等他们回。另外把之前的单元测试补了一些，覆盖率到了 70% 左右。

**输出**：
> 【支付模块】接入新版支付并完成对接，目前卡在第三方回调地址未提供、无法进入联调，需第三方支持后继续；【支付模块-测试】补充单元测试，覆盖率提升至约 70%，下一步继续补测。

**要点**：
- "等他们回 / 没法测"是明确阻塞 → 写成"目前卡在……，需……支持"，不隐藏。
- 覆盖率"70% 左右"是可保留的具体数据，照写（不拔高成"显著提升"）。
- 不确定的（具体还差哪些用例）→ 不编造，只写下步动作。

## 示例 7：高价值词用对 vs 拔高

**输入 A**（原文确有架构/性能动作，可用高价值词）：
> 今天把订单和支付那块本来搅在一起的代码拆开了，订单只管下单，支付单独一层，后面改支付不会动到订单了。顺手把那个列表大数据量会卡，我用虚拟列表重写了下，现在挺顺。

**输出 A**：
> 【订单/支付模块】完成订单与支付的边界拆分、解耦（订单仅负责下单、支付独立成层），降低后续相互影响；【列表组件】重构大数据量列表为虚拟列表实现，提升滚动流畅度（可复用：万级数据列表宜用虚拟列表规避卡顿）。

**输入 B**（只是普通小修，禁止拔高）：
> 改了个登录的小问题，按钮颜色不对，调了下。

**输出 B**（诚实，不拔高成"优化"或"重构"）：
> 【登录模块】修复按钮颜色显示问题。

**要点**：
- 输入 A 原文确有"拆分边界、解耦、重写为虚拟列表"的事实 → 用"拆分解耦""重构"是准确呈现价值，不是拔高，且每个词都带落点。
- 输入 B 只是改颜色 → 必须降级用"修复"，绝不能写成"优化登录体验"或"重构登录组件"。
- 高价值词的试金石：**原文有没有对应的结构/性能事实支撑**。有则用、落点要准；没有就老实用中性动词。

## 常见改写对照

| 流水账（删 / 改）          | 标准化（保留）              |
| -------------------------- | --------------------------- |
| 看了下                     | 阅读并梳理 / 评审           |
| 弄了下 / 搞了下            | 修复 / 补充 / 验证          |
| 处理了下                   | 定位并修复 / 梳理           |
| 沟通了                     | 对接并确认结论 / 形成……共识 |
| 参加了……会                 | （只保留结论/决定/待办）    |
| 学习了……（无结论）         | 删除                        |
| 跟进了                     | 推进 / 验证 / 确认进展      |
| 搞定了                     | 完成……（说清对象）          |
| 在做 / 在搞                | 当前阶段为……                |

记住原则而非死记这张表：**动词要能被"做没做到、做到哪了"检验。**

## 高价值工程词汇对照（用对 ≠ 拔高）

| 类型 | 可用词汇 | 仅当原文事实匹配时用 |
| --- | --- | --- |
| 架构 / 边界 | 架构设计、架构调整、分层、边界划分、领域建模 | 原文确有结构层面设计/调整动作 |
| 组件 / 抽象 | 组件化、组件抽取、组件复用、抽象、封装、解耦、模块化 | 原文确有抽取/封装/复用的具体动作 |
| 质量 / 性能 | 重构、优化、精简、提效、性能优化 | 必须指明优化对象与方向（耗时、体积、帧率等） |
| 发布 / 运维 | 迁移、灰度、回滚、压测、监控接入、治理 | 原文确有相应发布/运维动作 |

拔高红线（左 ❌ 禁止 → 右 ✅ 诚实）：

- ❌ 优化了下登录 → ✅ 仅当原文确有性能动作时写"优化登录接口响应耗时"，否则只是"修复登录 Bug"。
- ❌ 调整了下架构 → ✅ 仅当原文确有架构动作时写"拆分订单与支付边界"。
- ❌ 重构了下代码 → ✅ 仅当原文确有结构调整时写"将 Report 组件拆分为容器 + 展示组件"。
- ❌ 做了个组件 → ✅ "抽取 XX 公共组件并复用于 N 处"（要有复用事实）。

口诀：**每用一个高价值词，都要能回答"落到了什么对象、有没有可核实依据"。答不上就降级为中性事实动词——宁可平淡，不可虚高。**
