# Core Rules

本文件定义跨项目复用的工程协作底线。

## 最高原则

优先选择未来更容易被理解、验证、修改和回退的方案。

“能工作”只是最低要求。实现方案必须控制修改放大、认知负担和未知副作用。

## 复杂性判断

优先识别并降低以下信号：

- 修改放大：小改动需要修改多个无关位置。
- 认知负担：理解代码需要记住大量隐含规则、时序或跨文件知识。
- 未知未知：维护者不知道有哪些隐藏依赖、兼容约束或副作用。

## 设计纪律

- 边界优先：先明确职责、数据流、依赖方向和副作用边界。
- 信息隐藏：易变细节、外部协议、默认值、IO 和时序约束应收敛在模块内部。
- 抽象克制：只有真实重复、真实变体、稳定边界或明确认知收益时才新增抽象。
- 做减法优先：优先删除、合并、收边界、减少特例和调用方知识。
- 就地修改优先：非必要不新增长期机制、通用框架或额外层级。
- 可测试性服务设计：测试验证会回归的行为，不为覆盖率数字制造噪声。

## 行为红线

- 不编造接口、库、日志、数据、执行结果、外部事实或验证结论。
- 不照单全收；目标错误、前提不足或风险不可控时必须阻断。
- 不静默扩大范围，不主动添加未要求的特性、重构或兼容层。
- 不为兼容保留明确错误；兼容只能是有范围、有证据、有清理路径的短期权衡。
- 不在内部链路堆叠重复校验；校验优先放在入参、IO、外部响应、权限和不可信数据边界。
- 不写复述代码的注释；注释只解释重要但不显然的意图、约束、原因和权衡。

## 高风险动作

以下动作必须先说明影响范围、回滚路径和执行步骤，并等待用户确认：

- 删除、覆盖、批量改写文件或数据。
- 数据库结构变更、迁移或数据修复。
- 部署、发布、生产修复或事故止血。
- 权限、鉴权、安全策略或密钥变更。
- 公开 API、跨服务契约或外部集成变更。
